# 브라우저 성능 측정

화면 반응 측정 기록이다. API와 DB 측정은 [API·DB 성능 측정](03-server-performance.md)에 있다.

## 측정 환경

- 날짜: 2026-11-15 KST
- 기기: macOS 15.3.1, Apple M4
- 브라우저: Chrome (Playwright `channel: chrome`, 화면 있는 창, 1440×900)
- 조건: CPU 4배 감속, 캐시 비활성화 (Chrome DevTools Protocol)
- 화면: `npm run build` 후 `vite preview`, 백엔드는 임시 DB(시드 적재)를 쓰는 로컬 서버
- 스크립트: [refresh-scroll.mjs](../../scripts/perf/refresh-scroll.mjs)

## 갱신과 스크롤 · PERF-T05, PERF-T06

### 측정 대상

- 대량 트리: Cluster 20개와 Node 200개를 모두 펼친 상태 (행 2,220개, 열린 분기 220개)
- 스크롤: 매 프레임 24px씩 3초 스크롤, 3회
- 폴링 겹침: 35초 동안 위아래로 계속 스크롤해 30초 폴링이 한 번 겹치게 했다
- 값이 바뀐 갱신: 임시 DB에서 Node 심각도를 바꾸고 새로고침, 클릭부터 바뀐 값이 그려질 때까지 3회

### 결과 (스크롤 중 폴링 연기 적용 전 → 후)

- 스크롤만: 60fps, 가장 긴 프레임 17.7ms (전후 같음)
- 스크롤 중 30초 폴링이 겹칠 때
  - 적용 전: 폴링이 온 1초 구간 16fps, 가장 긴 프레임 417.5ms, 스크롤 중 API 요청 221건
  - 적용 후: 모든 1초 구간 60fps, 가장 긴 프레임 17.7ms, 스크롤 중 API 요청 0건
- 값이 바뀐 갱신 (응답 완료 → 화면 반영)
  - 분기 1개(cluster-01만 펼침): 20.5 / 31.9 / 23.1ms
  - 분기 220개: 454.2 / 457.8 / 457.9ms
  - 두 경우 모두 행 요소를 새로 만들지 않고 바뀐 값만 반영했다 (교체된 행 0개)

### 판단

- 스크롤 중 폴링이 겹치면 분기 220개 재조회 응답을 처리하느라 프레임이 끊겼다. 폴링을 스크롤이 멈추고 1초 뒤로 미뤄 겹치지 않게 했다. 수동 새로고침은 미루지 않는다.
- 몇 개 분기를 펼친 일반적인 갱신은 목표(200ms) 안이다.
- 분기 220개를 한꺼번에 펼친 갱신은 목표를 넘는다. 분기마다 요청을 따로 보내 응답 221개를 처리하는 비용이다.
  - 조회 결과 알림을 프레임 단위로 묶는 방법과 분기 조회 목록을 고정하는 방법을 시도했지만 개선되지 않아 되돌렸다.
  - 여러 분기를 한 번에 받는 API가 있으면 줄일 수 있지만 API 계약이 바뀌므로 이번 범위에서 제외했다.

## 빌드 이미지 기준 화면 반응 · PERF-T01 ~ T07

- 환경: [env.sh](../../scripts/e2e/env.sh)로 띄운 격리 환경(빌드한 이미지, nginx 경유 `localhost:13100`), 시드 적재
- 조건: Chrome, CPU 4배 감속, 캐시 비활성화, 실행마다 새 페이지, 3회
- 스크립트: [browser-perf.mjs](../../scripts/perf/browser-perf.mjs) (T01~T04, T07), [refresh-scroll.mjs](../../scripts/perf/refresh-scroll.mjs) (T05, T06)

### 결과 (3회)

- PERF-T01 첫 Cluster 표시·조작 가능 (목표 500ms): 352.7 / 167.0 / 164.7ms
  - 첫 회는 이미지를 다시 빌드한 직후라 백엔드가 데워지지 않은 상태였다.
- PERF-T02 펼침·접힘 (목표 100ms)
  - 첫 펼침(하위 조회 포함): 79.4 / 47.2 / 48.4ms
  - 접힘: 33.7 / 34.6 / 33.8ms
  - 캐시된 분기 다시 펼침: 33.5 / 33.0 / 32.8ms
- PERF-T03 검색, 요청 시작 → 결과 표시 (목표 300ms, 디바운스 제외): 61.2 / 42.6 / 42.8ms
- PERF-T04 필터 변경 → 트리 반영 (목표 200ms): 99.1 / 50.6 / 50.8ms
- PERF-T05 스크롤 (목표 55fps, 행 2,220개)
  - 스크롤만: 60 / 60 / 60fps, 가장 긴 프레임 17.7ms
  - 35초 연속 스크롤 중 30초 폴링: 모든 1초 구간 60fps, 스크롤 중 API 요청 0건
- PERF-T06 값이 바뀐 갱신, 응답 → 화면 반영 (목표 200ms)
  - 분기 1개: 25.5 / 25.8 / 31.6ms, 교체된 행 0개
  - 분기 220개: 452.9 / 464.3 / 446.2ms (목표 초과, 아래 한계 참고)
- PERF-T07 메모리 (참고 목표 300MB)
  - 첫 화면에서 탐색·검색·상세를 쓴 뒤 JS 힙 5.2MB, DOM 노드 957개
  - 행 2,270개를 펼치고 검색·상세를 연 뒤 JS 힙 24.3MB

### 측정 범위와 한계

- DB에는 Pod 100,000건이 있지만 화면은 펼친 부모의 직접 하위만 조회한다. 대량 목록 측정은 Cluster 20개와 Node 200개를 모두 펼친 2,220행(Namespace 2,000행 포함) 기준이다.
  - 이 상태까지 펼치는 데 Node 하나는 33ms, 220개를 연달아 펼치면 CPU 4배 감속에서 약 4.3초가 걸렸다.
- 탭 메모리는 Chrome 작업관리자 값을 자동으로 읽을 수 없어 JS 힙으로 대신 기록했다.
- 분기 220개를 한꺼번에 펼친 갱신은 목표를 넘는다. 분기마다 요청이 나가 응답 221개를 처리하는 비용이다.
