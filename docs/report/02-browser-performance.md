# 브라우저 성능 측정

---

## 이 문서는

- **목적:** 과제의 화면 성능 목표 7개(첫 화면 500ms, 펼침 100ms, 검색 300ms, 필터 200ms, 스크롤 55fps, 갱신 200ms, 탭 메모리 300MB)를 잰 기록이다.
- **주의:** 아래 최종 결과의 메모리는 JS 힙이다. 탭 메모리(작업관리자)는 "10만 행 펼침 개선"에 있다.
- **맥락:** 과제가 정한 조건(Chrome, CPU 4배 감속, 캐시 비활성화)으로 사용자가 실제로 하는 조작을 재현해 쟀다. Pod 10만 건이 들어 있는 DB에서, 운영과 같은 빌드 이미지로 띄운 화면을 대상으로 했다.
- **쓰임:** 목표를 넘은 항목은 원인을 찾아 고치고 같은 조건으로 다시 쟀다. 고치지 못한 항목은 한계로 남겼다.
- **읽는 법:** 맨 위가 최종 결과이고, 개선 과정은 아래 "측정 이력"에 있다. API와 DB 쪽은 [API/DB 성능 측정](03-server-performance.md)에 있다.

- 환경: [env.sh](../../scripts/e2e/env.sh)로 띄운 격리 환경. 빌드한 이미지 세 개(nginx 화면 `localhost:13100`, 백엔드, PostgreSQL), 시드 적재
- 브라우저: Chrome (Playwright `channel: chrome`, 화면 있는 창, 1440×900)
- 조건: CPU 4배 감속, 캐시 비활성화, 실행마다 새 페이지, 3회
- 기기: macOS 15.3.1, Apple M4

- Lighthouse 12.3.0, 데스크톱 설정, headless Chrome, 같은 격리 환경, 3회
- 3회 모두 성능 100, 접근성 100, 권장사항 100, SEO 100

### 측정 범위와 한계

- DB에는 Pod 100,000건이 있지만 화면은 펼친 부모의 직접 하위만 조회한다. 대량 목록은 Cluster 20개와 Node 200개를 모두 펼친 2,220행(Namespace 2,000행 포함) 기준으로 측정했다.
  - 이 상태까지 Node 하나를 펼치는 데 33ms, 220개를 연달아 펼치면 CPU 4배 감속에서 약 4.3초가 걸렸다.
- 분기 220개를 한꺼번에 펼친 갱신은 목표를 넘는다. 분기마다 요청이 나가 응답 221개를 처리하는 비용이다. 여러 분기를 한 번에 받는 API가 필요하다.
- 탭 메모리는 Chrome 작업관리자 값을 자동으로 읽을 수 없어 JS 힙으로 대신 기록했다.
  - JS 힙은 탭 전체 메모리가 아니다. 이 값으로 300MB 목표를 충족했다고 볼 수 없다.
- Pod가 한 분기에 몰린 경우(분기당 1,000건, 10,000건)의 펼침과 스크롤은 [페이징 검증](https://github.com/Lexyyaa/monitoring/blob/main/docs/report/04-paging-validation.md)에서 쟀다. 스크롤은 세 분포 모두 60fps였다.

## 측정 이력

### 스크롤 중 폴링 연기 (P03-08, 로컬 프리뷰 빌드)

- 조건: `vite preview`, 같은 CPU 4배 감속과 캐시 비활성화, 2,220행
- 스크롤 중 30초 폴링이 겹친 경우
  - 연기 전: 폴링이 온 1초 구간 16fps, 가장 긴 프레임 417.5ms, 스크롤 중 API 요청 221건
  - 연기 후: 모든 1초 구간 60fps, 가장 긴 프레임 17.7ms, 요청 0건
- 함께 시도했지만 개선되지 않아 되돌린 방법: 조회 결과 알림을 프레임 단위로 묶기, 분기 조회 목록 고정

### Lighthouse 지적 사항 수정 (P05-08)

- 처음: 성능 100, 접근성 100, 권장사항 100, SEO 82
  - 설명 메타 태그 없음, `robots.txt` 요청에 화면(index.html)이 응답됨
- 메타 태그와 `robots.txt` 추가 후: SEO 100, 접근성 96
  - 새 심각도 필터 버튼의 ERROR 배지(대비 3.95:1), UNKNOWN 배지(4.23:1)가 WCAG AA(4.5:1)에 못 미침
- 배지 글자 색을 진하게 바꾼 뒤: 네 항목 모두 100

### 10만 행 펼침 개선 (2026-11-25)

- **배경**
  - 최종 결과는 JS 힙만 쟀고, 스크롤도 2,220행에서만 쟀다.
  - 102,220행을 모두 펼쳐 다시 재 보니 탭 메모리가 3.3~4.0GB였다. 클릭 반응이 30초까지 늦어졌다.
- **원인**
  - 30초 할당 38.8GB 중 37GB가 TanStack Query `useQueries`의 결과 추적이었다.
  - 분기 하나가 응답할 때마다 분기 2,221개의 결과를 전부 다시 감쌌다.
- **작업 내용**
  - 하위 조회가 읽는 값만 추적한다 (`notifyOnChangeProps`).
  - TanStack Query를 5.62.7 → 5.108.4로 올렸다. 구버전은 관찰자마다 만든 `Error`가 GC 뒤에도 힙을 붙잡았다.
  - 분기별 행 캐시를 두어 바뀐 분기와 그 조상만 행을 다시 만든다.
  - `useQueries`, 폴링, 새로고침은 화면에 보이는 분기만 다룬다. 앞 갱신이 안 끝났으면 폴링을 건너뛴다.
  - 필터를 바꾸면 보이는 분기가 갱신 대상에서 빠지던 버그를 고쳤다.
- **지표** (격리 환경, 102,220행 모두 펼침, CPU 4배 감속, 캐시 끔, 같은 스크립트)
  - 탭 메모리 (작업관리자): 3.3~4.0GB → 138~183MB. 실행마다 달라 범위로 쓴다.
  - JS 힙: 1,298MB → 26~27MB
  - CPU (가만히 60초): 268% → 0%
  - 요청 수 (가만히 1분): 4,442건 → 12건
  - 새로고침: 3,656ms → 53~66ms
  - 펼치기/접기: 40~88ms. 페이지 첫 클릭만 64~152ms로 목표 100ms를 넘을 때가 있다.
  - 스크롤: 59.6~60fps, 폴링이 겹쳐도 최소 59fps
  - 회귀 확인: 프론트 테스트, E2E 10건 통과
- **트레이드오프**
  - 화면 밖 분기는 폴링하지 않는다. 화면에 들어와도 다음 폴링까지 최대 30초 늦다.
  - 하위 캐시를 지우지 않는다 (`gcTime: Infinity`). 필터를 바꿔 가며 오래 쓰는 경우는 재지 않았다.
- **측정 한계**
  - 수정 전 새로고침 3,656ms는 사용자 Chrome에서 직접 잰 값이다. 나머지는 자동 스크립트 값이다.
  - 수정 전에도 스크립트 스크롤은 60fps였지만, 직접 본 FPS 미터는 36.6fps였다. 메인 스레드가 화면 내용을 제때 그리지 못했다.
