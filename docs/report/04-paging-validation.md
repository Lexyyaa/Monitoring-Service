# 페이징과 대량 목록 검증

---

## 이 문서는

- **목적:** 검색 OFFSET 페이징과 트리의 한 번에 받는 하위 목록이 데이터 규모와 분포에 따라 어떻게 동작하는지 확인한 기록이다.
- **맥락:** README의 "아쉬운 점"에 큰 분기와 깊은 검색 페이지를 예상으로 적었다. 이번에는 실제로 재서 어떤 조건에서 개선이 필요한지 찾았다. 커서 페이징 도입은 미리 정하지 않았다.
- **읽는 법:** 맨 위가 판단 요약이다. 아래는 현재 구현, 측정 조건, 트리, 검색, 데이터 변경 순서다.
- **범위:** 측정과 재현만 했다. 프로덕션 코드와 API 계약은 바꾸지 않았다.

- **요구사항 위반 1건 (검색 결과 화면), 수정함**
  - 페이지 사이에 데이터가 바뀌어 같은 리소스가 두 페이지에 오면, 그 뒤 새로고침과 폴링이 성공해도 화면에 현재 데이터에 없는 행이 남는다.
  - 예: API 결과 49건인데 화면 51건. 이름이 바뀐 `pod-02-001-010`이 옛 이름으로 계속 보인다. 페이지를 새로 열어야 맞아진다.
  - "갱신은 표시 중인 데이터를 다시 읽는다"는 요구사항과 맞지 않는다. [아래](#확인된-요구사항-위반)
  - 페이지를 합칠 때 같은 리소스를 한 번만 남기도록 고쳤다. 컴포넌트 테스트 `SEARCH-T12`로 확인했다. OFFSET 누락은 남는다.
- **특정 규모, 분포에서만 나타나는 한계**
  - 결과 10만 건 검색(`pod-`)의 뒤쪽 페이지: 순차 p50 72ms(0페이지) → 210ms(마지막). 5 VU에서 104ms → 269ms
    - [ADR](../design/02-adr.md)의 재검토 조건(API 200ms 초과)에 해당한다.
    - 원인은 OFFSET 건너뛰기보다 일치 10만 건 전체 정렬이다. 디스크 정렬을 없애도(`work_mem` 32MB) 같았다.
  - 검색 결과를 많이 받은 상태의 갱신: 101페이지면 요청 101개를 차례로 보내 8.1초 걸린다. 30초 폴링마다 반복된다.
  - `ns-`는 페이지 위치와 상관없이 순차 약 112ms, 5 VU에서 약 270ms다. 대표 Node를 찾는 비용이다.
- **추가 결정이 필요한 정책**
  - OFFSET 페이지 사이 데이터 변경 시 중복과 누락: 계약에 정해져 있지 않다. 네 가지 모두 재현했다.
  - 갱신 때 받은 검색 페이지를 모두 다시 읽을지, 첫 페이지로 줄일지
  - 선택한 리소스가 삭제됐을 때 상세 패널 처리
- **문제가 확인되지 않은 항목**
  - 트리: Pod 1만 건 분기에서도 펼침 65~68ms, 스크롤 60fps, DOM 행 21~27개, 필터 62~88ms, 갱신 66~83ms
  - 검색 결과로 분기 9,001번째 Pod 열기: 9회 모두 경로, 선택, 가운데 스크롤, 상세가 정확했다.
  - 정적 데이터의 페이지: 순회 6종 모두 중복 0, 누락 0, 순서 일치, `hasNext`와 마지막 다음 페이지 정확. 오류율 0%
- **트리 페이징은 지금 필요하지 않다.** 1만 건 분기도 목표 안이고, 전송량(gzip 76KB)과 처리 비용이 작았다. 커서 페이징은 검색에서만 근거가 있다.

## 현재 구현

- **검색 페이지** ([ResourceSearchRepositoryImpl](../../backend/src/main/java/com/ocs/monitoring/infrastructure/persistence/resource/ResourceSearchRepositoryImpl.java), [SearchPageRequest](../../backend/src/main/java/com/ocs/monitoring/domain/resource/SearchPageRequest.java))
  - 페이지 크기 20, `page`는 0부터, 상한 없음 (`@PositiveOrZero int`)
  - 정렬: `lower(name)`, `resource_type`, `id` 오름차순. 종류 안에서 `id`가 유일해 전체 순서가 정해진다.
  - OFFSET: `page × 20`, LIMIT 21
  - `hasNext`: 21건을 읽었으면 참이고, 20건만 돌려준다. 총건수는 세지 않는다.
  - 4종 `UNION ALL` CTE를 만든 뒤 이름 조건, 정렬, OFFSET을 적용한다. Namespace는 행마다 LATERAL로 대표 Node를 찾는다.
- **트리**
  - 펼친 부모의 직접 하위만 요청한다. 하위 목록은 페이지 없이 전부 받는다.
  - Pod 목록: `node_id`, `namespace_id` 조건, `name`, `id` 정렬. 필터는 `issue_level` 조건을 더한다.
- **가상 스크롤** ([useVirtualWindow](../../frontend/src/shared/lib/useVirtualWindow.ts))
  - 트리 영역에만 적용한다. 38px 고정 행, 앞뒤 6행 여유
  - 행 배열은 펼친 분기 전체로 매 렌더 다시 만든다 ([buildTreeRows](../../frontend/src/features/resource-explorer/utils/treeRows.ts)). DOM에는 보이는 행만 그린다.
  - 검색 결과 목록은 가상 스크롤이 없다. 더 보기로 받은 결과를 모두 DOM에 그린다.
- **검색 결과로 이동** ([useResourceTree.openPath](../../frontend/src/features/resource-explorer/hooks/useResourceTree.ts))
  - 결과의 `path`를 따라 Cluster, Node, Namespace 하위 목록을 차례로 받는다 (캐시가 있으면 재사용).
  - 경로를 한 번에 펼치고 대상을 선택한다. 대상 행의 순번을 찾아 영역 가운데로 스크롤한다.
- **폴링과 수동 갱신** ([useRefresh](../../frontend/src/features/resource-explorer/hooks/useRefresh.ts))
  - 둘 다 `refetchQueries({ type: 'active' })`다. 펼친 분기마다 하위 목록 전체, 검색은 받은 페이지 전부를 다시 읽는다.
  - 검색은 TanStack Query `useInfiniteQuery`다. 다시 읽을 때 0페이지부터 차례로 같은 OFFSET을 요청한다.
  - 펼침과 선택은 행 key(`종류:ID:경로 Node`)로 유지한다. 스크롤 위치는 따로 저장하지 않고 DOM의 `scrollTop`이 그대로 남는다.
- **계약에 있는 것과 없는 것**
  - 있음: 정렬 기준, 20건, `hasNext`, 갱신 시 검색어, 필터, 펼침, 선택 유지
  - 없음: 페이지 사이에 데이터가 바뀔 때의 중복과 누락, 갱신 뒤 스크롤 위치, 트리 하위 목록의 최대 건수

## 트리: 분포별 비교

### 분포

- 세 분포 모두 Pod 총 100,000건이다. 대상 분기는 Node 1(`node-01-01`) + Namespace 1(`ns-01-001`)이다.
- 기본: [seed.sql](../../scripts/seed.sql) 그대로. 대상 분기 Pod 50, Node 1 Pod 500
- 1,000 집중: [concentrate.sql](../../scripts/paging/concentrate.sql) `hot=1000`. 대상 분기 Pod 1,000, Node 1 Pod 1,441
- 10,000 집중: 같은 SQL `hot=10000`. 대상 분기 Pod 10,000, Node 1 Pod 10,405
- 만드는 방법
  - 다른 Namespace의 Pod를 옮겨 총량을 유지했다. 옮긴 Pod는 `cluster_id`, `node_id`, `namespace_id`를 함께 바꿔 두 복합 FK를 지켰다.
  - Namespace마다 최대 5건만 빠져 모든 Namespace에 Pod가 남는다 (화면 경로 유지).
  - 심각도, 상태, 시각은 원래 값을 유지하고 이름만 `pod-hot-00001`부터 다시 붙였다.
  - 상태 집계 같은 파생 테이블은 스키마에 없어 맞출 데이터가 없었다.
- **부하 검증 조건이다.** Kubernetes 기본 설정은 Node당 Pod 110개가 상한이라 한 Node에 1만 개가 몰리는 배치는 실제로 드물다. 한 Namespace에 Pod가 수천 개인 경우는 여러 Node에 나뉘는 것이 보통이다.

### 평가

- **가상 스크롤의 렌더링 효과:** 행 수가 10,040개로 늘어도 DOM 행 21~27개, DOM 노드 333개로 같다. 스크롤은 빠르게 넘겨도 60fps다.
- **API 전송량:** 분기 크기에 비례한다. 10,000건 응답은 비압축 1.39MB, nginx gzip 75.7KB다. 백엔드 SQL 정렬 15ms가 응답 시간 대부분이다.
- **클라이언트 데이터 처리:** 응답 뒤 처리(JSON 파싱, 캐시 저장, 행 배열 구성)는 50건 20~27ms에서 10,000건 38~42ms로 늘었다. 긴 작업은 없었다.
- 이번 분포에서는 펼침, 스크롤, 필터, 갱신, 검색 이동 모두 문서의 목표 안이었다.

## 검색: 깊은 페이지

### 검색어와 페이지 위치

- 시드 데이터에서 결과 수를 세어 골랐다 ([search-order.sql](../../scripts/paging/search-order.sql)로 LIMIT 없이 같은 CTE 실행).
  - `pod-`: Pod 100,000건, 5,000페이지. 위치 0, 2500, 4999 (+ 빈 5000)
  - `ns-`: Namespace 2,000건, 100페이지. 위치 0, 50, 99
  - `-01`: 네 종류 31,886건(Cluster 1, Node 29, Namespace 290, Pod 31,566), 1,595페이지. 위치 0, 797, 1594
  - `pod-` + ERROR: 991건, 50페이지. 위치 0, 25, 49
- 같은 검색어, 같은 필터로 위치만 바꿨다.

  - `-01` 0 / 1594: p50 75.3 / 125.4ms, p95 78.9 / 162.9ms
  - `pod-` + ERROR 49: p50 54.9ms, p95 59.6ms
  - 8개 실행 모두 실패율 0% (130~180건씩)

### SQL 실행계획

- 방법: [search-plan.sh](../../scripts/paging/search-plan.sh). 백엔드와 같은 CTE에 `LIMIT 21 OFFSET n`, `EXPLAIN (ANALYZE, BUFFERS)` 3회. API 측정과 겹치지 않게 따로 실행했다.
- `pod-`
  - 0페이지: top-N heapsort(31kB), 78~84ms. 이름 조건이 모든 Pod에 맞아 100,000행을 읽고 조인한다.
  - 2500, 4999페이지: 100,000행 전체 정렬, 외부 병합 정렬(디스크 13.7MB), 206~217ms
  - 세션에서 `work_mem`을 32MB로 올리면 메모리 정렬(28.5MB)이 되지만 213~221ms로 같았다. 디스크가 아니라 전체 정렬 자체가 비용이다.
- `ns-`: 0페이지 top-N, 그 뒤 메모리 정렬(564kB). 세 위치 모두 117~130ms. Namespace 2,000개마다 대표 Node를 찾는 LATERAL이 대부분이다.
- `-01`: 0페이지 top-N 39~40ms, 797과 1594페이지 외부 병합 정렬(4.4MB) 79~85ms
- `pod-` + ERROR: 일치 991건이라 모든 위치가 7~8ms
- 정리: 비용은 "일치 건수"와 "0페이지인지"로 갈린다. 0페이지는 21건만 남기는 정렬, 그 뒤는 일치 전체 정렬이다. OFFSET 값이 더 커져도 비용은 거의 같다.

### 페이지 정확성 (정적 데이터)

- 방법: [search-traverse.mjs](../../scripts/paging/search-traverse.mjs). 0페이지부터 `hasNext`가 거짓일 때까지 받고, DB에서 LIMIT 없이 같은 정렬로 뽑은 목록과 한 건씩 비교한다.
- 전체 순회
  - `ns-` 100페이지 2,000건, `-01` 1,595페이지 31,886건, `pod-` + ERROR 50페이지 991건, `api` 1페이지 5건
  - 모두 중복 0, 누락 0, 순서 일치. `hasNext`인 페이지는 모두 20건, 마지막 다음 페이지는 0건, `hasNext` 거짓
- `pod-` 5,000페이지는 전체 순회 대신 앞, 가운데, 끝의 이웃 페이지만 비교했다 (0~2, 2499~2501, 4997~5000). 모두 일치, 4999에서 `hasNext` 거짓, 5000은 0건
- 같은 이름, 다른 종류 ([same-name.sql](../../scripts/paging/same-name.sql))
  - `lower(name)`이 `dup-name`인 Cluster 1, Namespace 2, Node 2, Pod 30건과 `dup-name-0` Pod 3건. 대소문자와 ID 입력 순서를 섞었다.
  - `q=dup-name` 38건, 페이지 경계가 같은 이름 묶음 안에 온다. 중복, 누락 없이 CLUSTER → NAMESPACE → NODE → POD, 종류 안에서 ID 순이다.
  - 종류 순서는 코드 문자열 순이라 NAMESPACE가 NODE보다 앞이다. 계약(`resourceType` 오름차순)과 같다.
  - 대문자 검색어 `DUP-NAME` + ERROR도 8건 모두 일치

### 더 보기 반복 (브라우저)

- 방법: [search-browser.mjs](../../scripts/paging/search-browser.mjs) `--mode more`. `pod-` 결과에서 더 보기 100회, CPU 4배 감속
- 결과 수, DOM 노드, JS 힙(GC 뒤)
  - 0회: 0건, 319개, 2.4MB
  - 1회: 40건, 692개, 2.9MB
  - 25회: 520건, 5,012개, 4.5MB

  - 100회: 2,020건, 18,512개, 8.5MB

- 클릭부터 20건이 늘어난 프레임까지: p50 111.8ms, p95 131.5ms, 최대 200.3ms

## 확인된 요구사항 위반

### 검색 결과에 현재 데이터에 없는 행이 남는다

- 재현 조건
  - 결과가 2페이지 이상인 검색에서 첫 페이지를 본 뒤, 정렬상 앞쪽에 리소스가 추가되거나 이름이 뒤로 바뀐다.
  - 더 보기를 누르면 같은 리소스가 두 번 온다 (OFFSET의 정상 동작).
  - 그 뒤 수동 새로고침이나 30초 폴링이 성공해도 화면이 API 결과와 맞지 않는다.
- 측정값: 위 화면 시나리오 4, 5, 7단계. API 40건에 화면 41행, API 49건에 화면 51행. 페이지를 새로 열면 맞는다.
- 원인 (코드와 재현 결과로 판단)
  - [SearchResults](../../frontend/src/features/resource-explorer/components/SearchResults.tsx)의 행 key가 `종류:ID`다. 두 페이지에 같은 리소스가 오면 key가 겹친다.
  - React는 key가 겹친 자식을 맞게 비교하지 못해, 데이터가 바뀐 뒤에도 옛 DOM 행을 지우지 못한다. 데이터(API 응답)는 맞고 화면만 틀린 점이 이 판단의 근거다.
- 사용자 영향
  - 없는 리소스나 옛 이름이 계속 보인다. 남은 행을 눌렀을 때의 동작은 확인하지 않았다.
  - 결과 수가 실제보다 많아 보인다.
- 개선안과 비용
  - 페이지를 합칠 때 `종류:ID`로 중복을 없앤다 ([useResourceSearch](../../frontend/src/features/resource-explorer/hooks/useResourceSearch.ts) 한 곳). 프론트 몇 줄과 컴포넌트 테스트 1건이다. 화면에서 중복은 사라지지만 OFFSET 누락은 남는다.
  - 누락까지 줄이려면 아래 "페이지 일관성 정책"의 결정이 필요하다.
- 수정 (P06-06)
  - 위 첫 개선안을 적용했다. 같은 리소스가 다시 오면 처음 나온 위치의 행만 남긴다.
  - [search.test.tsx](../../frontend/tests/component/search.test.tsx) `SEARCH-T12`: 결과 41건에서 첫 페이지 뒤 맨 앞에 1건을 추가하고 더 보기, 새로고침을 한다.
    - 수정 전 코드에서 실패, 수정 뒤 통과했다.
    - 더 보기 뒤 39행 모두 다르고, 새로고침 뒤 화면이 응답 40건과 같은 순서다.
  - 프론트 `format:check`, `build`, `npm test` 42건 통과
  - 빌드 이미지와 실제 DB로 브라우저 재현을 다시 하지는 않았다. 격리 환경은 수정 전에 내렸다.

## 성능 한계와 개선안

### 결과가 많은 검색의 뒤쪽 페이지

- 재현 조건: 일치가 수만 건 이상인 검색어(`pod-` 100,000건, `-01` 31,886건)의 1페이지 이후
- 측정값: `pod-` 순차 p50 72 → 210ms, 5 VU p50 104 → 270ms. `-01` 35 → 79ms
- 사용자 영향
  - 더 보기를 반복하는 사용자가 아니면 뒤쪽 페이지를 거의 열지 않는다. 화면에서 2,020건까지 받아도 클릭 반응 p95 132ms였다.
  - 서버 부하가 더 크다. 동시 사용자가 늘면 한 요청이 300ms에 가까워진다.
  - `ns-`처럼 페이지와 상관없이 무거운 검색어도 있다 (5 VU 270ms).
- 개선안
  - 커서(키셋) 페이징: 마지막 행의 `(lower(name), resourceType, id)` 다음부터 21건을 받는다.
    - 기대 효과: 모든 페이지가 0페이지처럼 top-N 정렬이 된다. 0페이지 측정값(순차 72ms)이 기준이다. 일치 행을 모두 읽는 비용은 그대로다.
    - 비용: API 계약 변경(`cursor` 입력, 응답에 다음 커서), OpenAPI, ADR, 프론트 `getNextPageParam`, 테스트. `page` 번호로 바로 가는 기능은 없어진다 (지금 화면에도 없다).
    - 이 효과는 측정하지 않았다. 도입 전 같은 데이터로 전후를 재야 한다.
  - 페이지 상한 또는 넓은 검색어 안내: 계약에 상한을 두거나, 결과가 많으면 검색어를 좁히라고 안내한다. 구현은 작지만 사용 흐름이 바뀐다.
  - `work_mem` 증가는 효과가 없었다 (메모리 정렬도 같은 시간).
  - `ns-`의 대표 Node 비용은 페이징과 별개다. [ADR 운영 기준](../design/02-adr.md)의 "200ms 초과 시 재검토"에 해당하므로 따로 검토가 필요하다.

### 검색 페이지를 많이 받은 상태의 갱신

- 재현 조건: 더 보기로 101페이지(2,020건)를 받은 뒤 새로고침, 또는 30초 폴링
- 측정값: 검색 요청 101개를 차례로 보내 8,082ms. 그동안 새로고침 버튼이 잠긴다. 폴링마다 반복된다.
- 기존 갱신 목표(변경 부분 200ms)는 "몇 개 분기"와 "분기 100개 이상" 트리 조건으로 정의되어 있어 이 경우와 직접 비교하지 않는다.
- 개선안
  - 갱신 때 검색은 앞쪽 몇 페이지만 다시 읽는다 (TanStack Query `maxPages` 또는 갱신 시 첫 페이지로 초기화). 프론트 수정이지만 "갱신해도 받은 결과 유지"와 충돌하므로 정책 결정이 먼저다.
  - 검색 결과 목록에도 가상 스크롤을 적용하면 DOM 증가(결과당 약 9개)는 막는다. 갱신 요청 수는 그대로다.

### 큰 트리 분기 (지금은 문제 아님)

- 10,000건 분기도 모든 목표 안이었다. 다만 응답 크기와 SQL 정렬은 건수에 비례한다 (1.39MB, 15ms).
- 통계 추정(1,046행)이 실제(10,000행)보다 작아 정렬을 고른다. 집중이 실제로 생기면 다시 측정한다.
- 트리 페이징을 넣는다면 검색 결과에서 대상 행으로 바로 가는 방법이 함께 필요하다.
  - 지금은 분기 전체를 받아 대상 순번을 찾아 스크롤한다.
  - 페이징 뒤에는 대상이 아직 받지 않은 페이지에 있을 수 있다. 검색 결과의 대상 `(name, id)`를 기준으로 "그 행 앞뒤 N건"을 받는 조회가 필요하다.
  - 가상 스크롤의 전체 높이를 정하려면 분기 건수가 필요하다. 지금 API에는 건수가 없어 계약 추가가 필요하다.
  - 측정 근거가 없어 지금은 제안하지 않는다.

## 결정이 필요한 갱신, 페이지 일관성 정책

- **페이지 사이 데이터 변경**
  - 현재: OFFSET이라 앞쪽 추가는 중복, 앞쪽 삭제는 누락이 생긴다 (A~D 재현).
  - 선택지
    - 그대로 두고 화면 중복만 없앤다. 누락은 다음 갱신 때 채워진다 (갱신이 받은 페이지를 모두 다시 읽으므로).
    - 커서 페이징: 앞쪽 추가와 삭제(A, B, D)로 인한 밀림은 없어질 것으로 예상한다. 이름이 바뀐 리소스(C)는 옛 이름과 새 이름으로 두 번 보일 수 있다. 측정하지 않은 예상이다.
    - 한 시점의 결과를 고정하는 방식은 지금 데이터 모델(이력 없음)로는 만들 수 없다.
- **갱신 때 받은 검색 페이지 범위**: 모두 다시 읽을지(지금, 정확하지만 101페이지 8초), 앞쪽만 다시 읽을지
- **선택한 리소스가 삭제됐을 때**: 지금은 이전 상세와 404 안내를 보여 준다. 요구사항에 정의가 없다.
- **갱신 뒤 트리 스크롤 위치**: 지금은 브라우저 scroll anchoring에 맡긴다. Chrome에서 맞게 동작했고 다른 브라우저는 확인하지 않았다.

- Chrome 외 브라우저의 scroll anchoring
- `pod-` 5,000페이지 전체 순회 (앞, 가운데, 끝 이웃 페이지만 비교)
