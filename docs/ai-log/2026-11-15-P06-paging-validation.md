# 페이징과 대량 목록 검증

- 한 일
  - 새 격리 환경 `monitoring-paging`(포트 13200, 18200, 55200, 새 볼륨)을 띄웠다. 기존 두 환경은 건드리지 않았다.
  - 총 Pod 10만을 유지한 채 한 분기에 1,000, 10,000건을 모은 부하 분포를 만들어 트리를 비교했다.
  - 결과 10만, 3만, 2천, 991건 검색어로 첫, 중간, 끝 페이지를 순차, k6, SQL 계획으로 따로 쟀다.
  - 페이지 사이 추가, 삭제, 이름, 상태 변경을 API와 화면에서 재현했다.
  - 검색 결과를 합칠 때 같은 리소스를 한 번만 남기도록 고치고 `SEARCH-T12`를 추가했다.
  - 측정 스크립트를 `scripts/paging/`에 두고 결과를 [보고서](../report/04-paging-validation.md)에 썼다.
- 확인
  - 트리는 1만 건 분기에서도 펼침, 스크롤, 필터, 갱신, 검색 이동이 목표 안이고 정확했다.
  - 정적 데이터의 검색 페이지는 중복, 누락, 순서 오류가 없었다.
  - 결과 10만 건 검색은 뒤쪽 페이지가 약 3배 느렸다. 원인은 디스크가 아니라 일치 전체 정렬이었다.
  - 페이지 사이 변경 뒤에는 갱신이 성공해도 검색 결과에 없는 행이 남았다. 페이지를 새로 열면 맞았다.
  - `SEARCH-T12`는 수정 전 코드에서 실패하고 수정 뒤 통과했다. 프론트 테스트 42건 통과
- 결정
  - 커서 페이징은 검색에만 근거가 있어 제안으로만 남겼다. 트리 페이징은 제안하지 않았다.
  - 검색어 입력 측정은 실제 이름(`payment`)으로 다시 쟀다.
  - README는 main의 현재 문구를 유지한다.
  - `pod-` 5,000페이지 전체 순회 대신 앞, 가운데, 끝 이웃 페이지를 DB 순서와 비교했다.
- 남은 일
  - 수정 뒤 실제 이미지와 DB로 브라우저 재현은 다시 하지 않았다.
  - 페이지 일관성 정책, 갱신 범위, 삭제된 선택 처리는 사용자 결정이 필요하다.
